# Review of e43cd01 (fix/ayla-overrides, package A, AY25 / DB10)

Checked: gocheck (vet ok, 457 pass / 0 fail), clean merge into main 8cc7ae7 (`git merge-tree`: no conflicts), read of aylaoverride.go, api.go hunk, dispatch.py, legionctl.py, dashserve.py, instances.go, docker-compose.yml.

## Who can reach the API (AY25: only the owner sets overrides)
- Engine listens on `:8090` (main.go:31, no auth). It runs in rathena's network namespace, published as `127.0.0.1:8090` (docker-compose.yml:50). Every process in that namespace (both OpenKore containers, legion, legion-core) and every process on the host can POST and DELETE.
- Puppet masters today cannot: dispatch.py:203-206 runs `claude --tools Bash --permission-mode dontAsk` with only `Bash(python legionctl.py:*)` (plus ayla.sh actions, bugq add) allowed; curl/python -c are denied. legionctl.py has no override subcommand and no generic call, and `DENIED_CTL` (dispatch.py:153) does not list one. The Haiku helper has the same limits; bots run in-process and never call HTTP.
- So there is no hole today, but the owner-only property rests on "no tool happens to expose it", not on a guard. Two near-term paths break it:
  1. dashserve.py:724 forwards any `POST /api/...` to the engine unauthenticated; package F will add DELETE. Anyone who can reach the dashboard port can set or clear an owner override.
  2. Any later legionctl subcommand (package G "owner orders go to A's store") is allowed to puppet masters by the blanket `legionctl.py:*` pattern and would also be an owner-override write unless added to `DENIED_CTL`.

## Findings
- major, legion/aylaoverride.go:254 (Set), :317 (Clear), api.go:808 (route) / AY25: `SetBy:"owner"` is hard-coded and the write endpoints are unauthenticated, so the "owner only" claim is not enforced. Not a live blocker (nothing calls it yet, no reachable caller today), but it must be fixed before package B/F/G land. Smallest guard: a per-host owner token in a git-ignored file (for example `legion/data/owner.token`, created by the dashboard server), sent as `X-Owner-Token` only by dashserve.py for owner-initiated override calls; POST/DELETE without a matching token answer 403 (GET stays open). Add `legionctl` override verbs to `DENIED_CTL` or simply never give puppet roles the token path. A separate localhost listener works too but the netns is shared with OpenKore, so the token is better.
- major, legion/aylaoverride.go:131 (aylaOv singleton) + instances.go:96 (coreForward) + docker-compose.yml:157,182: main and core share `./legion/data` read-write, but each process loads the store once and never reloads. Ayla's party runs in core; `/api/ayla/overrides` is answered by the main instance (not forwarded). Package B hooks in core would never see an owner override, and a sweep or set from core would overwrite the file from stale memory and drop rows set via main (lost update). Fix now: forward `/api/ayla/overrides` to the core instance in coreForward so one process owns the store, or re-read the file by mtime under the mutex before every read and write. Not harmful at this commit (no consumer), but package B is unsafe without it.
- minor, legion/aylaoverride.go:305 and api.go handler: when the store write succeeds but the audit append fails, Set returns `(o, err)` and the handler answers 400 although the override is stored and in force. Answer 200 with a warning field.
- minor, legion/aylaoverride.go:325: Clear only matches rows not yet expired. A row that expired but is not yet swept answers 404 instead of "already expired"; harmless.
- minor, legion/aylaoverride.go:76 ovMapRe accepts any name; `spawnsByMap` empty is a warning only (confirmable). A typo map plus confirm=true would be stored. Consider rejecting maps absent from the map list outright.
- minor: gofmt reports unformatted files in main, none are this branch's.

## Checked and fine
- Atomic write: temp file in the data dir, fsync, rename; failure removes the temp file; memory changes only after the file write succeeded (copy-on-write rows).
- Restart: file reloaded on first use; unreadable file moved aside to `.bad-<ts>`, not overwritten; active unexpired rows stay in force; expired rows are not served (activeLocked checks time) and swept on the next read.
- One active per kind: Set ends every active row of the kind as "replaced" and logs the replaced id. Tested.
- Expiry sweep: runs on Active/List, logs one audit line per row, history trimmed to 50 plus actives.
- Default-off: no code path reads aylaDirective yet; the new GET/POST/DELETE are the only behaviour, so Ayla and every other party are untouched. No tuning flag needed. No gate (G05, G12, G13, G19, G20, G25) is touched; nothing is keyed on her name.
- Tests (aylaoverride_test.go, 6) cover precedence, expiry, replace, persistence, farm-map confirm and API; they would fail without the file since the symbols do not exist. They use temp dirs, not live data (G23).

The two majors do not harm live play at this commit (dark code), but the owner-only guard is the stated first check of the brief and must be added with the first consumer. Merge is acceptable as dark code provided the guard and the single-owner store are required before package B, F or G merges.

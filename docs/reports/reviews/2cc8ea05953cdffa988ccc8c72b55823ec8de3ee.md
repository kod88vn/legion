## Findings

- major, partycons.go:27: `ms[0].pin` is read with no lock. Every writer holds the bot's `b.mu` (engineparty.go:82-84,
  humanparty.go:536-538 and :561-563, aylarotate.go:461-465), and the existing reader `Bot.pinned()` (humanparty.go:89) locks it.
  So it is a real data race (pointer write vs read; `go test -race` would flag it if a test ran both). In practice the
  pointer is word-sized and the stale value is harmless (one tick), but it is a race. Fix: `p := ms[0].pinned()` (takes
  b.mu only for the read; partyPerfOffset's "no bot locks" means the caller holds none, so it cannot deadlock; check the
  callers ai.go:2115/2150 and guildlead.go:362 hold no bot lock, which the comments say), or better, key on the party's
  own flag (`Party.Engine`, set by startEnginePartyFor, engineparty.go:71) so no bot field is read. The comment in the code
  ("takes no party or bot lock") states the race as a feature.
- minor, gearscore.go offsetCons: the start value -10 is applied only when the perfState is created. If the state already
  exists with off 0 (flag flipped on later, or a pin acquired after the first call) the party keeps its old step and only gets
  the death/step-up/floor rules. Flipping the flag therefore does not give "starts at -10" to parties already tracked until
  a restart. Acceptable for staging, but say so when the owner flips it.
- minor, gearscore.go:265: partyPerfOffset returns 0 when `gearPerfOn()` is off, so the rule is silently inert then.
- minor, test coverage: TestPartyConsEngineParty and the flag tests only exercise partyConsFor on bare Bot structs; no test
  runs partyPerfOffset end to end with the real tracker and a pinned leader. The offset maths are covered
  (TestPartyConservativeSteps, Floor, OffKeepsOldStart).
- minor, process (PR02): the owner's order is not recorded under docs/rules/ (no line in parties.md, archive.md or
  coverage.md; grep for conservative / start 10 / 20 min finds only lessons-index and reports). It exists only in commit
  messages (b3b07d2 "owner: party too weak", ea10c2a). Record it with an ID.

  engine_parties gets the rule (TestPartyConsEngineParty, also checks a non-listed leader gets nothing). Solo path:
  `offset()` is a one-line wrapper with cons=false; every changed branch is guarded by `cons`; TestPartyConsOffKeepsOldStart

- Rule vs the owner's words (taken from the commit messages b3b07d2 / ea10c2a / the brief, since the order text is not in
  docs/rules): start -10: matches. One death steps down 5 at once: matches (`max(-20, off-5)`, window restarted, even

  +3, where the Ayla script uses +3). Floor -20: matches the brief (the solo floor stays -15, perfMin; cons uses -20 only
  when cons is set). Not implemented here, present in the Ayla script: the HP-under-50% step down of -3. The owner order as
  quoted does not ask for it.
- Engine-party-only by default vs the owner order: the order was given as "party too weak" for Ayla's party (partylead.pl,
  5acb7d8) and the earlier engine port ea10c2a generalised it to every bot party with the flag ON. The owner order, as far
  as it can be read, was about parties being too weak in general, and the 2026-11-15 brief calls it a "conservative party map
  rule" without limiting it to Ayla. So default OFF for ordinary bot parties is a narrowing of the order, defensible by
  PR40/Constitution 2.8 (new behaviour is proven on Ayla's party first) and cheap to undo (one flag). Recommendation: keep the
  staging for this merge (merge as is), file the flip of `party_conservative_on` to true as the next step right after the
  rule is seen working on the engine party (deaths per hour, map choices), and tell the owner plainly that until then
  ordinary bot parties are not under the order. Do not hold the merge for it.
- Race on ms[0].pin: see the major finding above.
- Interplay: the step feeds partyPerfAdjust (ai.go:2115 up-only, :2150 down-only) and guildlead.go:362 before the EC39 gear
  gate; the gate then caps `minLv` at the gear level only if the step lifts above it (`g > 0 && minLv > g`). A -10..-20 step
  can only lower the level, so the gate never binds more than before and cannot raise a choice. The -20 floor is below
  the solo -15 only for cons parties; no code reads perfMin elsewhere for a party in a way that breaks (grep: gearscore.go only).
  The up-only call clamps negative to 0 and the down-only call clamps positive to 0, so a cons start of -10 shows up
  only in the down call: the party is lowered immediately, as intended.
- Mutation (scratch merge): start changed to 0, the death step disabled and partyConsFor forced false: three of the new
  tests fail (TestPartyConsEngineParty, TestPartyConservativeSteps, TestPartyConservativeFloor). Restored and removed.
- Rules: no gate touched (G05/G06/G20 not involved; no live data, no Docker, nothing sent to Ayla). Behaviour sits behind a
  tuning flag default false, with the engine-party exception.

## Verdict

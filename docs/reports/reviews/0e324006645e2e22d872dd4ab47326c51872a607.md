## Major
- `legion/data.go:391`, `legion/fairgate.go:11,34`: the gate only filters `SpotsFor`, the fallback picker (`ai.go:884`, reached only after the 85% guide-spot pick fails or when no guide spot fits). `guideSpotsFor` (`strategy.go:173`), `goodHere` (`ai.go:~660`, guide OR SpotsFor), `beginnerPick` and party picks are not gated. The bugq maps are guide spots (`strategy.go:55,59`: gef_fild05 18-32, pay_fild07 20-35) but only for levels up to Max+3, so the lv45 / lv53 cases are caught only through the fallback. A lv40-56 bot on a guide spot such as gef_fild10 or moc_fild03 can still sit on maps whose monsters are under its fair line (base-15). The fix removes part of the symptom, not the cause (0 fair kills). Needs the same fair-share test in `guideSpotsFor` or a documented reason it is out of scope.
- `legion/fairgate.go:11` with `ai.go:884`: the gate measures fairness at the effective level (`powerLv()`, gear based), but the meter counts fair kills at base level (`meter.go:173`, `BaseLvOr()`). A well-geared bot (powerLv above base) is gated too hard and loses spots that are fair for its base level; a badly geared one (powerLv below base, the lv53 Monk case if its gear score is low) gets pay_fild07 back because the floor is computed from the lower number. Use base level for the fair test.

## Answers to the questions
- No spot at all: the gate can empty `SpotsFor` for a level (test 2 shows it does for lv45 with only gef_fild05). Guide spots go to level ~107 and are ungated, so with 85% probability a bot still gets a guide spot; the other 15% falls to `ai.go:886`, which now sets idle with `Set: "auto (nowhere reachable)"` and `huntRetry` +1 min (the 105cd4e fix). The bot idles (in town or where it stands, goal Map = current map) for a minute, then re-plans and most likely takes a guide spot. No permanent stall; cost is a minute of idle for the 15% case. Odd classes/high levels (99, transcendent) were not checked against live map data (no Docker/DB); guide spots cover them, so I rate this low risk.
- Travel: effect is small, because the gate sits on the fallback only. Where it removes the nearest fallback spot the bot takes a farther one (hop penalty in the score at `ai.go:~915` already weighs it); no code reduces hops. Not measurable without live data; the 32.8% travel share will barely move either way.
- Party map choice: unaffected. `leaderPartyPick` / `partyMapNear` / `partyMapOK` never call `SpotsFor` (grep), so PT35 band code on main is not touched. Party members use `guideSpotsFor`. Solo bots only.
- Re-plan thrash: the new condition (`ai.go:541`) adds hunt goals marked "nowhere reachable". Once chooseHuntingGround sets a normal `Set: "auto"` goal the retry stops, and failure re-arms a 1-minute `huntRetry`, so at most one plan per bot per minute; `goodHere()` is tried first so a bot already on a good map keeps it. A bot whose guide pick is random (85%/15%) may hop between a far guide spot and idle across retries but only while the result stays "nowhere"; no loop found. The empty-spots branch does not reset `b.route`; harmless (set again on a successful pick).
- New default-on behaviour: `fair_spot_gate_on` defaults ON (rules say behaviour changes default off, reviewer.md step 3). The owner's PR37 says built things are on, so I note it and do not block on it.

verdict: do not merge

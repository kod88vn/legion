## Findings that are still on main
- major, `legion/tuning.go:369-371` and `legion/aylarotate.go:312`: rotation is ON by default (`AylaRotationOff` is a
  negative flag, zero value false). The owner stopped it; the only thing holding it stopped is `ayla_rotation_off: true`
  in `legion/data/tuning.json:69`, a runtime data file. If that file is replaced, reset, restored from an older copy
  or the key is lost, the engine starts swapping a member of Ayla's party within 3 hours of the first
  `lg.LastAt == 0` pass, against the owner's order and G20. Fix: invert the default (a positive `ayla_rotation_on`,
  default off) or remove the feature path from the tick; add a test that the zero-value tuning does not rotate.
- minor, `legion/aylarotate.go:305-312`: `rotationTick` works on `humanPartyNow()` (a party with `Human != ""`). After
  the AY24 switch Ayla's party is an engine party with no human, so rotation is a silent no-op there. The handoff
  machinery (`handoff.go`, `handoffSelect` at startup, `instance_handoff.json` overrides) stays active and still
  applies stale overrides to the profile list on every start; document or retire it with the feature.
- minor, `legion/aylarotate.go` (`rotationTick`, `inBot := instanceBotFor(inP)` then `rotApplySwap`): relies on
  `instanceBotFor` never returning nil; it does not today.
- minor, tests (`aylarotate_test.go`): they cover `pickRotation`, handoff stamps, the in-place roster edit and the
  bug-queue line. There is no test of `rotationTick` with the default tuning (the defect above) and none of a
  double-login race between the two instances.

## Side effects on other parties
Rotation takes bots from the main instance only when its candidate snapshot is under 5 minutes old and never a guild
leader, trader, brewer or pinned bot. No effect on other parties while off.

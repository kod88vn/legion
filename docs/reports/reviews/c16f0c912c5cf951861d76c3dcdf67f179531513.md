## Major

1. `tools/system/gatecheck.py:58-73` (point 1): `fieldcheck.run_all()` is called with defaults, so every `gatecheck.py --coverage` run (after every rule edit) docker-cps the live npc tree (about 30 s) and checks every container, stopped ones too. Today that returns mismatches (Ayla 456 flag maps + 8 portals; QA/legacy 100 walk maps, 1,500+ portals), so every rule commit fails, and rule recording (PR02) is blocked. It also fails when docker or rathena is unreachable (`OSError` becomes "could not run"). Fix: gatecheck calls `run_all(containers=[])` (repo only), against a cached server snapshot (for example `legion/data/fieldcheck-server.json` or a copied tree with an mtime check, refreshed by the watchdog), and treats "no server data" as a skip with a warning, not a FAIL. Containers stay with the watchdog and the start check.
2. `tools/system/fieldcheck.py:19-23,147-152` and `openkore/gen_fields_from_mapcache.py:49-52` (point 2): the flag-only differences will not go away on recreate. The repo field files exist only for maps whose WALK bits differed (the generator skips a map when `(old&1)==(new&1)` for all cells). The 456 flag-only maps in Ayla's container are therefore stock OpenKore fields, absent from `fields-re` and `fields-srv`, so neither overlay nor image bake touches them. The repo copies carry the server's bits only for their own 341 maps (hence 0 repo mismatches). Result: Ayla's container stays "mismatched" forever and the watchdog keeps a high-priority bug open (`field_pass`), which is noise, and a true bug is buried in it. Routes use the walk bit only; snipe/water flags do not decide routing. Fix: report kind `flags` as a note (not a problem) by default, or add `--strict-flags`; if the owner wants exact flags, regenerate the repo copies with `all_maps` (a larger image) as a separate decision.
3. `openkore/overlay.sh:19-43` (not changed by the branch; point 3): the start overlay copies and self-checks only `fields-re`, never `fields-srv` (97 files). The branch adds `fields-srv` to the Dockerfile bake only. With the compose `/ok-src` mount and a stale image, the 97 `fields-srv` maps are not fixed on recreate, and the new check will then flag them. Add the same loop for `fields-srv` (and mount it; QA mounts only `./openkore/fields-re:/qa-fields`, `docker-compose.yml:138`). Without it the baked fix works only after an image rebuild.

## Minor

4. `tools/system/watchdog.py:503-540` (point 4): the hook is filing only (`p.file`/`p.close`; no restart, no `docker start`). It is gated to once an hour or on a container start edge (`fc_up`), and is skipped in dry runs and when `fields=None`. It does run docker cp (npc tree, about 30 s, timeouts up to 900 s each) synchronously in the watchdog pass, which also starts containers and writes the heartbeat; a slow check can leave the 90 s lock stale (`LOCK_STALE`) and delay restarts. Run it in a thread/subprocess or refresh the lock/heartbeat around it. The start trigger repeats on every flapping restart (Ayla crash loop = repeated 30 s checks); add a minimum gap.
5. `watchdog.py` `docker_prefix()` (WSL distro aware) and `fieldcheck.docker_prefix()` differ (`wsl docker` default distro); on a machine with several distros the check may read a different docker. Reuse one helper.
6. The 8 stale Ayla portals (point 3): `fix_re_portals.sh` only owns Izlude lines. The rest are covered only if `portals-srv.txt` has matching "-" lines and `overlay.sh` runs `fix_srv_portals.py` (it does, lines 51-53). I could not verify the 8 against the stopped container (no Docker). The deploy agent should run `fieldcheck.py --container ro-openkore-ayla` after the recreate and expect 0 portal-drop.
7. QA/legacy containers: about 100 walk-bit maps and 1,500 portals differ. They are legacy or stale and not routed by the overlay. They will keep a high bug open until recreated or removed; consider limiting the watchdog filing to containers in use (Ayla, QA) and marking legacy as info.

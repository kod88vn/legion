### major
- engineparty.go:~44-70 and humanparty.go:~507 (AY24): the `startEnginePartyFor` path (API `/api/.../human party` at api.go:627, or a leftover `human-parties.json`) pins every member (`m.pin = &Pin{...}`) but `goalTick` (lfg.go:626) skips pinned bots unless `inHumanParty(b)`, and an engine party has `Human == ""`. Its members would get no farm goals, and about 26 other `pin != nil` gates apply. The restore path (the one the migration uses) does not pin, so the real cut-over is not hit, but the two paths behave differently. Do not start Ayla through the API path; or drop the pin / extend the goalTick condition to `p.Engine`. Not harmful while the switch is off.
- Hand-over from Zen.fox to Ayla (partypersist.go syncBotParty, `lv.leader != lv.char` branch): the code does it. The current in-game leader (a member that is online and in the party under the same name) sends `0x07da` with Ayla's account id, retried every 30 s. It only works if the in-game party is already named exactly "Ayla pt" (the migration and humanparty use that name) and Zen.fox is online and in `p.Members`. If her old in-game party has another name, Ayla leaves it (first `case`, line ~625) and founds a new one, and the others leave and re-join one by one. No test covers this branch, and it is the one step that decides G19/G20 at cut-over. Needs a test, or the deploy agent must check the name before the cut-over.

### minor
- partypersist.go:~692 and engineparty.go persistsBotParties: the flag is read once when `botPartyKeeper`/`restoreBotParties` start. Setting `engine_parties` after the core is up gives no saver and no restore until the next core restart. The cut-over order (migrate, set flag, then start core) must keep that order; the compose comment says it.

- tools/system/ayla_engine_migrate.py: `--userid` falls back to the literal "player" when the OpenKore config has no `username`; the persona is then written with a wrong login name. `persona_entry` deep-copies `personas[0]`, so any field not overwritten (e.g. inventory, home, memory hints) is inherited.
- docker-compose.yml: the `openkore-ayla` container still exists. At cut-over it must be stopped before legion-core logs her in, or the two sessions kick each other (G19). The compose comment does not say so.

## Migration script safety
Dry run by default and prints no password. It never deletes: `human-parties.json` is renamed to `.pre-ayla-engine`, and `personas.json` is copied to `.pre-ayla-engine` first. It refuses when any other human is in `human-parties.json`, when the `.pre` file already exists, when `parties_engine.json` holds other parties, and when no password is found. The second run changes nothing (tested). It touches no database. Order caveat: the rename happens before the persona is added; a failure in between is recoverable by hand and the second run then completes the rest. The 7 tests are real (state compared before/after) and would fail without the guards.

## Verdict on the points asked
- Flags off, nothing computed: `marketEngineRound` returns first on `!tune().MarketEngineOn || !stockDue`, before any lock or
  snapshot. Both flags default false (`TestMEOffByDefault` checks defaultTuning, zero runs, endpoints). The only always-on cost is
  one `tune()` read per econRound. The data.go change adds one int field and one switch case (parse cost only).
- Deviations from the brief: (1) the two economy.go wiring lines are necessary and minimal (one call after guildStockRound, one
  registration); acceptable. (2) data.go `Mob.WalkSpeed`: needed for the Fast flag; additive, acceptable.
- Information only (EC43): no guild direction, no bot command, no Bot method called. The only reads of bots are the already built
  econSnap fields (name, lv, guild, nextPiece, keeper) and `s.b.P.Account` (never reassigned anywhere, so safe unlocked). Only side
  effects: in-memory meState and data/market_feed.json. The feed carries no set_by or direction. Good.
- Pure core: meNeeds / meAllocate / meEvaluate / meBuildFeed take a snapshot and read no globals (meNeed uses constants), no maps
  iterated into output order without sorting; rotation is keyed on `Now`, so it is deterministic. Tests cover it.
- Allocation math matches the design: per item min(12, max(1, ceil(30% n))), per map 5, ordered floor(70% n), held orders count
  toward all caps, rotation start moves hourly, 6 h recent rule (taken only when value >= 2x best non-recent), Creamy need capped at
  10 with the +50 bonus applied before the cap, ranks of 3. Value = min(remain, Y*H) * price * heal mult * (1-risk) / (1+travel/30),
  /1.3 for Fast. Remain is reduced as farmers are placed (water-filling). Sensible.
- Yields and drop rates: `meMapsFor` uses `pieceFarms`, which calls `effDropRate` (droprate.go) on each drop, so server multipliers
  are applied (item type -> item_rate_card / common / etc., boss variant, capped at 100%). Y = Rate(percent) / 100 * 3 kills/min * 60.
  Correct given Rate = effRate/100 in percent. It is right only while tuning `drop_rates_from_conf` is true (live
  data/tuning.json has it true; default is 1x) or drop_rate_mul is set; with the conf read, Card = item_rate_card (500 in the
  import). Not a bug in this change, but the engine inherits that switch. Kill rate is a fixed 3/min and ignores spawn count and
  mob HP: documented as unverified in the header.
- Locking / runtime: meLiveSnapshot takes econ.mu (stockDemand, copy and release), dynPrices.RLock, gstock.Lock, opps.Lock one at a
  time, never nested, never b.mu; all compute (meEvaluate, pieceFarms per item) runs with no lock held; meState is locked only to
  swap pointers. Called at most every guildStockEvery (5 min) from econRound after the stock round, in the econ goroutine. Cost:
  a few hundred items x pieceFarms (map lookups, sort of at most a few dozen rows) per 5 min: negligible.
- Atomic write: temp file in the same dir, Sync, Close, Rename, temp removed on every error path. Write errors are printed, not fatal.
  Test `TestMEFeedAtomicWrite` uses t.TempDir. Tests touch no live data (G23); tuning is swapped through curTuning and restored.
- Endpoints: both return `{"status":"off",...}` when the flag is off; on, a nil feed is handled (`guildOf` has a nil receiver check),
  meState lock released before encoding the feed. No existing API JSON changed (new routes /api/market/engine and /api/market/feed
  only; no overlap with existing registrations).

Minor:
1. marketengine.go:34 header and :567 `meFeedMissingWP2` still say the mob speed field is not read and Fast is always false, but

3. marketengine.go:665 `pieceFarms(id, 200, 8)` keeps the 8 best maps by drop rate x spawn count, before the per-farmer level filter in
   meOptions. If the best 8 are all high-level mobs, a lv 15-30 farmer sees no option for that item. Consider a larger n or filter by band.
4. marketengine.go:388 ordered cap is a floor, so 1 farmer gets no order and 3 farmers get 2. Matches the stated "floor", fine for
   the real roster; note for tests with tiny fixtures.
5. tuning.go (new struct lines): `MarketEngineOn` / `GuildMarketFeedOn` are not gofmt-aligned. Run gofmt on tuning.go (the file
   was already unformatted on main for older lines, so this is only cosmetic).
6. No test covers the live path (`meLiveSnapshot`, `meMapsFor`, the WalkSpeed parse). Flag-off keeps it harmless; WP-level
   verification with market_engine_on will need live evidence (Constitution 3.6): `/api/market/engine` runs > 0 and a sane
   data/market_feed.json.
7. Live farmers have no Held, Recent or Travel yet (WP3 fills them): allocation is a pure offer list, as intended.

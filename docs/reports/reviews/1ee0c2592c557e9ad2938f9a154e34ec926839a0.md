## Findings

- blocker, partycons.go:31 (`ms[0].pinned()`) with ai.go:2588-2606 (`leaderPartyPick`): self-deadlock on the leader's `b.mu`.
  `leaderPartyPick` is documented and run with `b.mu` held (ai.go:546 -> chooseHuntingGround ai.go:766 -> leaderPartyPick), and
  `ms[0]` is the party leader, i.e. `b` itself (party.go:240 `Members: append([]*Bot{leader}, ...)`; the call site requires
  `p.Leader == b`). It calls `partyMapOK(ms, cur)` (ai.go:2610) / `partyMapNear` -> `partyFitLv` -> `partyFitLvRaw` (ai.go:2149) ->
  `partyPerfAdjust` -> `partyPerfOffset` -> `partyConsFor` -> `ms[0].pinned()` -> `b.mu.Lock()` while the same goroutine holds
  `b.mu` (sync.Mutex is not reentrant). It is reached whenever `party_conservative_on` is off (the default: the flag short-circuit
  returns before `pinned()` only when it is ON), gear performance is on (default true) and the leader and its status are online and
  published. So with the defaults, every bot-party leader whose goal is dropped would freeze its own bot goroutine and anything
  waiting on its lock. The "callers hold no bot lock" comment (partycons.go:25, gearscore.go:238) is wrong for this caller.
  Reproduced: a scratch test took `l.mu.Lock()`, called `partyFitLv([]*Bot{l, m})` with the flag off and gear perf on, and hung
  until a 3 s timeout (FAIL "partyFitLv with the leader's b.mu held never returned"); the test was removed after the run.
  The previous review's advice ("check the callers hold no bot lock") was exactly this check, and it fails.
  Other callers checked: guildlead.go bestPartySpot (member locks are released before partyPerfOffset at :362; its callers
  guildlead.go:475/601/816, bosshunt.go:443, humanguildlead.go:355 not traced to a held bot lock), lfg.go, lfg_human.go, party.go
  partyFitCheck (no bot lock held, parties lock released before), and the ai.go:2310/2484/3328 helpers are documented "no bot
  locks" and are called from those. `leaderPartyPick` is the one that breaks it.
  Fix: do not take `b.mu` in partyConsFor. Key the rule on a party-level fact set when the engine party is made (a `Party.Engine`
  field as engineparty.go:71 sets, or a lock-free atomic/copy of the pin character stored beside `pin`), or have `leaderPartyPick`'s
  caller pass the pin. Add a test that runs `partyFitLv` / `leaderPartyPick` with the leader's `b.mu` held.
- major (test gap that let this through): TestPartyConsEndToEnd calls partyPerfOffset with no lock held, so it cannot see the
  deadlock. Mutation: replacing `ms[0].pinned()` by the direct field read `ms[0].pin` leaves all 7 partycons tests green (the
  race is back and nothing notices); no test holds the leader's lock.
- minor, gearscore.go:225-227 (consOn): the check is once per tracker, so it cannot reset repeatedly (a flapping pin or flag leaves
  `consOn` true and the old/`cons` rules just apply or not). Mutation (the `consOn` block disabled): TestPartyConservativeSteps and
  TestPartyConsEndToEnd fail, so it is tested. One unfair case: the first application overwrites the existing step with -10, so a
  tracker that had already earned a step above -10 loses it, and one that had fallen below -10 (down to the solo floor -15) is raised
  to -10, which is less conservative for a party that is dying. Accumulated death steps are not kept. Acceptable at flag flip, but
  better `s.off = min(s.off, partyConsStart)`.
- minor, gearscore.go:262: the rule is inert while `gear_perf_on` is off (now documented in the comment).

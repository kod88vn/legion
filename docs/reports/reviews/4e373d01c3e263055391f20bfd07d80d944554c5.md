## Findings

### major
1. `tools/sentinel.py:341-346,483` (and `partycheck.py`, `aylalog.py`, `dashserve.py`, `dispatch.py:828`; no release anywhere). The lock is never released on a clean exit. The sentinel exits on purpose with `sys.exit(2)` after every outage (that is how it wakes the main session); its lock then stays fresh for up to 300 s, so the relaunch by the main session or the keep loop hits `take_lock` -> False -> `main()` prints "not starting" and returns None (exit 0, silent). Result: after each outage wake the sentinel is dead for up to 5 min while the caller believes it restarted; the same delay hits a normal restart of any of the five scripts (dispatcher 3 min, dashboard 2 min). The crash case is fine (stale takeover works: `common.take_lock` replaces a lock older than `stale`; lock refresh is inside every loop turn, which is shorter than the stale limit for all five). Fix: release the lock when the holder exits (atexit/finally: remove only if `lock_owner` is our pid), and make a refusal exit non-zero.

### minor
- `dispatch.py:767-772`: the lock is taken before `other_instance_alive()`; on that refusal (return 3) the lock stays held for 180 s by a dead pid, and `--force` is then refused by `take_lock` as well. Take the lock after that check, or release it.
- `dashserve.py:775-778`: the lock is taken before the port is bound; a failed bind (port in use) leaves the lock fresh for 120 s and blocks a restart. A second dashboard on another port for development is also refused unless `--no-heartbeat` is given.
- `common.py:139-147`: `take_lock` checks the age, then `remove` + `O_EXCL` create; two simultaneous starters can both succeed. The loser of the file race exits at its first refresh (owner pid differs), so no lasting double copy, but for a dashboard the surviving copy may be the one that failed to bind, leaving none until the lock is stale.
- `sentinel.py:348`: if `common` fails to import (`SYSC` None) the lock is skipped silently; acceptable, the same import also drives the heartbeat.

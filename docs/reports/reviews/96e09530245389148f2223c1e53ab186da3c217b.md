## Findings
- major (not a regression, but the owner's complaint stays open in one mode), partylead.pl:3891 / 3893 / 4098 vs 706-708: the crossing fight-back lives only in `travel_mode_tick`. `tick` returns earlier at `stick_tick` (3891), `pack_tick` (3893) and `portal_guard` (4098, before `travel_mode_tick`), and `pack_tick`'s own wait branches (3536-3596, the dungeon/entrance wait at ~3478-3510, the "wait: stand where she is" end at ~3591-3596) return 1 with no fight-back. On a trivial crossing map `travel_mode_tick` has already set `attackAuto = 0` (`$trivSaved`), and it stays 0 while those branches hold her. She then stands, route and move cleared every tick, and is hit unanswered. The only fight check there is line 3471 (`AI::inQueue('attack') && ai_getAggressives()`), which needs an attack already queued. This is the case the owner described (crossing, waiting for the priest). Suggested fix: call `fight_back()` (guarded by the same `$triv` condition) at the top of `tick`, before `stick_tick`, or in `pack_tick` before each wait `return 1`.
- minor, partylead.pl:2965-2970 (first-sample gap): a monster first seen already attacking (total above 0 on its first sample) is not counted; it becomes current only on its next hit. The test at the "total seen for the first time" case asserts this. Cost: one attack interval (about 1-3 s, longer for slow or casting monsters) in `fight_back`, and in the rally path an attackAuto target is cleared by `AI::clear('attack')` until then (rally_tick ~786). The gap is wider than the fixer says, because sampling runs only where `nearest_attacker`, `rally_tick` or `fight_back` is called. A monster that hits during a stick/pack/portal return is untracked until a later sample, and if it was never sampled before it is a first sample. Suggest treating a first sample with a total above 0 as a hit now (a monster entering the list already hitting is a real attacker); or sample once per `tick` before `stick_tick`.
- minor, partylead.pl:2962: `%attackSeen` / `%attackAt` are never pruned (no map-change reset, no removal of vanished monsters). Slow growth over days and a small chance of a reused monster ID inheriting an old time. Prune IDs not in `getItems()` in `attacker_sample`.
- minor, partylead.pl:3806-3818 (boss pull-back, existing): every 3 s it clears `attack` and routes away with `attackOnRoute 0`, so she does not fight back a monster hitting her while a boss is within 14 cells. Deliberate escape; not changed here.
- minor, tests: `partylead_flow_test.pl` covers the helpers only (`current_attacker`, `nearest_attacker`, `rally_gather_hold`). No test calls `rally_tick`, `travel_mode_tick` or `pack_tick`, so the call order above is unproven. The new tests fail on dbbe10f only because the helpers are missing.
- Behaviour defaults: new behaviour is on with no `tuning.json` flag (reviewer.md asks for one). This is a bug fix for Ayla (AY21 deploys at once) and only adds fighting back, so not blocking.
- Other parties: no effect, only `openkore-ayla/` changed.

No blockers. The major is an existing gap this commit does not widen, and the commit is a strict improvement, so merging is safe. A follow-up fix for the pack/stick/portal early returns is needed before the owner's complaint can be called closed.

verdict: merge

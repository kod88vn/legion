# Review of cb4cf4d (fix/ayla-hookin, package B: owner overrides wired into the engine party, AY25)

Rules checked: AY25, DB10, G13, G20, G25, PR16. Merged into a scratch copy of current `main` (7a98459, packages A, C, D in): clean auto-merge, `tools/dev/gocheck.sh` on the merged tree: vet ok, pass=518 fail=0 skip=28, gofmt notes are the existing ones. Scratch worktree removed.

## Unchanged behaviour (ok)
Every hook is behind `ovEngineParty(p)` (`p.Engine` and the leader in `engine_parties`), so with `engine_parties` empty, and for every other party, `ovPartyMap` is "", `ovFireOrders` finds no party, `ovGuildDirFor` returns nil, and `partyCmdCall(owner=false)` is the old `partyCmdLead` (the `return true` after the single call is ignored by it). No name test on Ayla (G25/PR16 ok). `TestOvOffForOtherParties` covers it. No default-on change (no tuning key needed: the whole path needs an owner override plus `engine_parties`).

## Major

1. party.go:~519-526 (and the gates at ~502-508) - the owner farm map is still behind partyFitCheck's delays; AY25 "takes effect" is not met. The owner check sits after the `list` build, so a change waits for: `now.Sub(last[p]) < 5min`, `now.Sub(p.MovedAt) < 15min`, `fitHold` (up to 10 min after arrival, up to 45 min while the party has not arrived), the first-sight spread (0-5 min after every Legion restart) and `Formed < 2min`. A party that moved 3 minutes ago takes the new owner map 15+ minutes later, and one still walking to its map up to 45 min. No test calls `partyFitCheck`, so none of this is proven. Fix: apply the owner map in a pre-pass before the gates (only `bossActive`/`isRestoring` and "already on it" skip), and add a test that sets an override on a party with `MovedAt` = now and expects a relocate on the next round.

2. ai.go:2513-2551 (`leaderPartyPick`, also lfg.go:~818 `leaderGoalSync`) - other movers are not owner-aware and move the party straight off the owner map with `p.moveTo`. Worst case is the very death loop the brief calls deliberate: `deathLoopCheck` sets `b.badMap = last.m` for 30 min before the new "override kept" return; when the dying member is the leader and its goal drops, `leaderPartyPick` sees `bad(cur)`, picks `partyMapNear` and moves the party away (the same happens when `partyMapOK(ms, cur)` is false for the weakest member). The party then oscillates: away, then back by the next fit check 5-20 min later. Fix: in `leaderPartyPick` (and the item-goal move in `leaderGoalSync`) return the owner map when `ovPartyMap` is in force; do not set `badMap` for the owner map in `deathLoopCheck`. Needs a test through `leaderPartyPick`.

## Minor

3. party.go:1548+ (`OvDone`) - fired-order records are memory only. A Legion restart (or a core restart) while the override is still in force (default 24 h, `ovDefaultHours`) re-fires town_run "now", rally and follow_me. For a town run that sends Ayla's party to town again, hours after the owner meant it. Acceptable only if it is documented; better to persist the id in the override store (a `fired_at` field) or to give the order kinds a short default expiry (for example 10 min). The same retry loop means an order that cannot run (leader on a trip for hours) fires late, whenever the leader next can.

4. party.go ovFireOne rally case - `startRallyAt` returns false for "rallies off" (`rallyOn()`: `rally_enabled` false and `rally_bot_share` 0, as the code comments say tuning.json ships) as well as for "on cooldown". The order then retries every round, silently, with no log, until the override ends. Split the two: log and finish ("rallies are off") when `!p.rallyOn()`.

5. partycmd.go partyCmdCall(owner=true) - returns true even when no member was far (nothing said), so the order is consumed with only the "members called" log line. Harmless but the log is untrue; also `p.Members` is read without `parties` lock (as before).

6. ai.go deathLoopCheck - the owner branch returns before relocate but after `b.badMap` is set (see 2); the "override kept" event is the only record. The brief's "log is enough" holds for the log line itself (event on the dying bot, with map names), but it fires per death-pair, not a dashboard flag. OK for now.

7. guildduty.go ovGuildDirFor - gated on `humanGuildID` plus any non-empty `engine_parties`, not on her party being up; `seen` key uses ItemID/Map of the owner row only. Fine. Free text becomes `dirLevel` with the text as note: ok.

## Checked and fine
- Override expiry: `Active` is time-checked, `ovPartyMap` goes ok=false, the party simply stays on the last map and the normal fit rules take over; no stale state besides `OvDone` (which is keyed by override id, so a new override re-fires).
- `startRallyAt`: split of `startRally` is behaviour-identical for the old caller; `rallySpot(town, town)` works (town spawn fallback). `partyCmdCall`: lock use matches the old caller (`b.mu` held); the call from `ovFireOne` locks `l.mu` and takes no `parties` lock inside, so no inversion.
- Tests cover map, expiry, death loop (relocate-level only), guild dir, orders once, other parties, free text. They do not reach `partyFitCheck` or `leaderPartyPick`, which is where findings 1 and 2 live.

Findings 1 and 2 mean an owner map order is late (up to 15-45 min) or undone by the party's own pickers, which is the exact thing AY25 must guarantee.

verdict: do not merge

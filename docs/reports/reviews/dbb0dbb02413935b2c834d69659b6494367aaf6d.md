### Major (file as queue items; none changes play, so none blocks the merge)

M1. `legion/marketmetrics.go` (price stability); design 3.5 says 24 h. The stddev is cumulative since the counters began
and persists across restarts (`mmSaved.PriceN/PriceSum/PriceSq`), so it never forgets. After a deploy such as dynamic
pricing (EC48) the early samples dominate for weeks, so the meter cannot show better or worse after a change (3.2, 3.6).
The fixer admits it; I agree it is a real gap, and the JSON does not say it (only the doc does). Judgement: file, not fix
now: nothing consumes `within_target` for a decision. Must be fixed before price stability judges any deploy. Fix: keep
per-item hourly buckets (n, sum, sumsq) for the last 24 h and compute over them; add a `window` field ("cumulative" until
then).

M2. `legion/marketmetrics.go` (`marketMetricsRound` need, coverage). Need counts only bots short of their `nextPiece`; the
engine's `stockDemand` is excluded, so coverage divides by a smaller need than the engine sees and can read high. Supply is
farmer supply only and nothing calls `noteMMSupplied` yet, so `coverage.overall` reads 0.0 with status `ok` (a real zero,
but not a measurement of supply). Judgement: file, not fix now. Fix: add `stockDemand` units with the same hour-peak rule,
or name the metric `build_piece_coverage`; report `no_supply_source` with null `overall` until a supply hook is wired.

M3. Two sets of farmer counters exist once `fix/farmer-orders` merges (below). Reconcile before that branch is merged.

## Farmer counters: two sets now

`marketmetrics.go` keeps `offers`, `accepts`, `declines[reason]`, `deaths`, `farmerH` and `supplied[band][item id]` in
`market_metrics.json`, fed by `noteMMFarmerOffer/Accept/Decline/Death/Hours` and `noteMMSupplied`. `fix/farmer-orders`
(65620be, `legion/farmers.go`) keeps its own `farmerCounts` in `farmer_counters.json`: `Accepted`, `Declined[reason]`,
`Supplied[item name]` (no band), `Deaths[account]`, changed by `farmerCount` at farmers.go lines 260, 297, 301, 357, 363 and
shown by `farmerCountersSnapshot`. That branch calls no `noteMM*`, has no offer count and no farmer-hours. They would
disagree: supply keyed by item name against band plus item id; deaths per account against a total; the unsafe-map decline at
line 260 is counted without a counted offer; separate files with separate `since`.

Recommendation: the metrics file is canonical. It is flag-independent, it is what `/api/market/engine`,
`/api/meter/market` and `progress.py` read, and it already holds band, item id, offers and farmer-hours, which coverage and
deaths per farmer-hour (design 3.5) need. In `fix/farmer-orders`: (1) at each `farmerCount` site also call the matching
`noteMM*` (offer at the start of the offer handler, accept, decline with the same reason string, death, supplied with the
band from `meBand(level)` and the item id, hours from the session length); (2) make `farmerCountersSnapshot` read through
`marketMetricsBlock(...)["farmers"]` and drop `farmer_counters.json` (read it once into `mm` as a migration if wanted);
keep per-account deaths only as a detail beside the same total. Merge `fix/market-metrics` first, rebase
`fix/farmer-orders` on it, and add a test there that accepted and declined after the same events equal the metrics block.

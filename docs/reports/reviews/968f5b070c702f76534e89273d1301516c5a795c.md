## Findings

### blocker
1. The engine era cannot work; it finds no party. tools/system/aylawatch.py:ayla_party (about line 129) selects the party
   whose `human` is Ayla. In the engine era the party is formed with `formPartyOpt(leader, rest, "", ...)` and
   `Party.Human` stays "" (legion/engineparty.go:60-95), so `/api/parties/detail` has no `human` field and no
   `Human:true` member for her; she is an ordinary bot member with `leader:true` and the party name is botPartyName. Result:
   every engine-era snapshot says "no party with human Ayla" and all fields are None. The tests pass only because
   `test_aylawatch.py` builds an invented fixture (`party()` with human=Ayla and a human leader row) that the real API
   never produces for the engine era. The party must be found by a member named Ayla (leader), not by `human`.
2. Engine-era distance to the leader does not exist. `dist_lead` is filled only in the `p.Human != ""` branch
   (legion/partydash.go:145-150); for an engine party the members carry no `PartyMemberExtras`, so `dist_lead`, `kpm`,
   `exp_h` are absent from the JSON (the code reads them with `_int(..., -1)` and silently reports -1/0). Distance has to
   be computed from member x/y/map (the fields exist) in the engine era. Same cause: `exp_h` per member is missing, so
   `exp_h`/`exp_5m` are 0 or wrong.

### major
3. `meter_bots.json` field names are wrong. `read_meter_ayla` takes `data["ayla"]` and reads `exp_h`, `kills`, `zeny`,
   `kpm_plugin`; that row is a `meterBotOut` (legion/meterapi.go:546-570, aylaBotOut) with name, class, lv, map, online,
   min, kpm, zph, par_kpm... and none of those four fields (they exist only in `aylaView`, the meter API, not the file).
   So `meter_ayla` and the zeny fallback are always empty, and `own_exp` is always 0. The row is also built from the
   OpenKore view (`Instance:"openkore"`), so in the engine era it is likely stale. Use `kpm`, `zph`, `map`, `online`.
4. Printed line loses information the `.sh` gave. aylawatch.sh printed lock_map, intent (60 chars), the last two
   `[watchdog]` lines and the status.json age. They are in the JSON record but `summary()` prints none of them; the main
   session reads the printed line. Print them (the stuck/watchdog and status-age fields are how she is judged alive).
5. Constitution 3.8: the heartbeat is written but no watchdog entry checks it (tools/system/watchdog.py lists aylalog,
   sentinel, partycheck ... not aylawatch), so a dead watcher is not noticed or restarted. Needs a watchdog row
   (hb aylawatch.heartbeat, stale > 360 s because a round can take 300 s + 60 s of docker).

### minor
6. In the engine era `exp_5m` is an estimate from hourly figures (exp_h*5/60), `kills_5m`/`deaths_5m` are deltas of
   running totals from the previous record; they are None on the first round and wrong if a bot is replaced or a counter
   resets (negative deltas are not clamped). Label it as estimate in the line.
7. The loop catches only OSError; any other exception (KeyError, TypeError on an odd API shape) ends the process; the
   missing heartbeat then shows it (if finding 5 is fixed), so acceptable, but a logged `except Exception` round guard
   would keep the meter reading (3.2).
8. The leaderboard.py docstring change is a docstring only; the `.sh` also did not call it, fine.

## Conclusion
The OpenKore era (the era that runs today) is sound and read-only. The engine era was written from code reading and does
not match the real API: it cannot find Ayla's party and has no distance. The branch claims both eras.

verdict: do not merge

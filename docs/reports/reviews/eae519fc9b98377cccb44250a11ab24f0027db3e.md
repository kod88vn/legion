## Findings

### major
- tests/system/test_livedata_guard.py:21 `STACK_OWNED` is a suffix match (`fn.endswith`) on any file, in any
  subfolder. A test that writes `*.heartbeat`, `*.lock`, `watchdog.status.json`, `bugq.wake` or `bugq.wake.state`
  into live data passes the guard. These are exactly the files the tests exercise (watchdog, dispatch, bugq tests).
  Better: do not exclude by name; compare each excluded file by content/owner instead (the heartbeat/lock holds a pid or
  epoch written by the stack: a test-written one carries the child's pid, so record the child pids and fail if an
  excluded file holds one of them), or fail on an excluded file that is new or deleted (the stack keeps them present) and
  only ignore mtime/size changes. Cheapest sound option: for excluded names require "existed before and exists after".
- tests/system/test_livedata_guard.py:46-48 the guard is not safe to run in the main checkout while the stack or the
  dashboard runs: it compares size+mtime of EVERY other file in legion/data, and the stack writes many that are not
  excluded: `puppet_heartbeat.json` (does not end in `.heartbeat`), `bugqueue.jsonl`, `health.log`, `meter.jsonl`,
  `deploys.jsonl`, `watchdog.log`, `watchdog-reports.jsonl`, engine json files (friends, levels, guild_*, econ_counters).
  A run during live play fails spuriously (false positives) for up to 53+ s of window. It never touches or writes live data
  itself (read-only os.walk/stat), so it is safe in that sense, but it will cry wolf and train people to ignore it.
  Fix: compare only files a test could plausibly write, or take two snapshots with no child in between and subtract
  files that changed in that idle interval (stack-noise baseline), or compare against the child's own writes by running
  the child with a recording hook.
- tests/system/test_livedata_guard.py:42-44 child return codes are ignored. A child that dies on import (or hits the
  900 s timeout, which raises TimeoutExpired and leaves the child running) proves nothing, yet the guard can pass. Assert
  `returncode == 0` or at least that "Ran N tests" appears in the child output; kill the child tree on timeout.

### minor
- The guard has no sensitivity proof: no test plants a write (for example a child run with a deliberately leaking
  module, or a unit test of `snapshot` diffing). "Fails without the fix" is not demonstrated; the old code popped
  LEGION_DATA, so reverting testenv in one module would be caught only by a run in a checkout whose live folder is
  written to. Add a unit test of snapshot/diff and one planted-leak child run.
- In a git worktree `legion/data` holds only tracked files, so the guard checks almost nothing there; it is meaningful
  only in the main checkout (where the false-positive problem above applies).
- Tools that resolve the data dir WITHOUT LEGION_DATA (hard-coded `legion/data`): tools/variety.py:23-24,
  tools/wrongbuilds.py:19,160,167,302, tools/pairchars.py:19-20. No test imports them today (grep clean), so no current
  leak, but a future test would bypass isolation silently. The guard would catch it only if the file is not excluded.
- tests/dashboard/fake_engine.py has no isolate() (not a test module; harmless, it is imported by a test that does).
- Tests that run subprocesses with LEGION_DATA unset on purpose (tests/system/test_system.py:475) only import and print
  a path; verified no writes. Other subprocess tests inherit the isolated env.

### Major
1. legion/starveillead.go:206 (switch off is not exactly unchanged): the lead loop ticker goes from 1 min to 15 s for everyone.
   With `ayla_engine_on` off each tick still runs `starveilAutoLead()` and `humanGuildInfo()` (a file read, line 214), now 4x as
   often, and fund/party rounds fire up to 45 s earlier than before. Gameplay effect is small, but the brief and the
   "behaviour behind a flag that defaults off" rule are not met. Fix: tick every 60 s when off (or sleep 15 s only while the switch is on);
   TestAylaEngineOffChangesNothing does not cover the interval.
2. legion/starveillead.go:322 plus package C (tuning key mismatch): `ayla_engine_on` (bool, package D) and `engine_parties` (string of
   human names, package C, engineparty.go:enginePartyOn) are two independent switches. Turning D on without C's engine party in
   core leaves no master bot in core: `/api/human-guild/engine` answers 409 (line 424ff "master is not online in core"), the
   OpenKore hand-off is already stopped (line 322), so Starveil gets no warn/expel/invite/say at all. Turning C on without D keeps
   the OpenKore hand-off, which is fine. Need one switch (or D reading `enginePartyOn`) before the owner flips either.
   Textually they merge clean; behaviourally they must be tied together. This is not harmful while both are off.

### Minor
3. legion/starveillead.go:384 starveilExec "kick": core executes whatever AID/CID main posts and has no G20 guard of its own
   (the guard is only `starveilDutyOK` on main, `!s.core && !s.keep && !s.pinned`). Defence in depth: refuse a kick whose
   Char/AID is a bot of this core instance or Ayla's party. Same for "invite" (no validation of AID).
4. Reachability of the new endpoint (/api/human-guild/engine): it is registered on every instance but answers only when
   `coreInstance()` and `ayla_engine_on`. The core API is `127.0.0.1:8091` inside the rathena network namespace; it is not published
   to the host (docker-compose publishes only 8090) and `coreForward` (instances.go:110ff) forwards only /api/human-party, /api/party-turn
   and /api/bots|memory/<core bot>, so `/api/human-guild/engine` is NOT reachable through :8090. Puppet masters (host side, via 8090) cannot reach it, and on the main
   instance it returns 409. Anything in the rathena/legion namespace (including Ayla's OpenKore container and legion processes) can
   still POST to it, unauthenticated, to expel or invite. Same trust model as the rest of the API, so acceptable, but finding 3's guard would shrink the exposure. Do not add it to coreForward.
5. legion/economy.go:1695 G12 on the buyer side of a market trade also blocks Ayla's own purchases from another player when they would leave her under 10,000z
   (the deal is cancelled, `d.close`, no zeny floor reason surfaced to a retry). G12 reads as "sending away zeny"; a trade price is that
   strictly, but this does block normal shopping below the floor. Owner should confirm the intent. NPC buys (town.go 0x00c8, dietrich.go 0x09d6, identify/trap/alchemy)
   are untouched, which matches "only sending away", and there is no other vending-buy path in the engine.
6. G12 coverage is otherwise complete for sends: mail (mail.go:72, fee included via `mailCost`), trade price/gift (economy.go:1695),
   guild fund donations and gear gifts (through `giftableZeny`, gearpool.go:817, used by humanguildlead.go:96,391 and gearpool pools).
   The tests (starveillead_test.go:259,278) only test the pure helpers `aylaSpendOK`/`aylaGiftCap`, not the mail/trade/giftableZeny call sites, so
   removing those hooks would not fail a test.
7. `aylaSpendOK` is keyed on the name via `isAyla`, like the existing G12 helpers; the new engine code itself gates on guild master / tuning, not on her name, so G25 holds
   (duty exemptions for pinned/core/keep and the recruit pick treat humans and bots the same).

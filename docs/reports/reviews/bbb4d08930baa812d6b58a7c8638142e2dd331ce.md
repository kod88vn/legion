## Findings

### minor
1. `common.py:176-190`, takeover race remains. Starters A and B both read a stale age. A replaces the stale file aside and creates its fresh lock; B then runs `os.replace(p, aside)` on A's fresh lock without re-checking it is the stale one, removes it and creates its own. Both starters return True. The window is microseconds and the loser exits at its first refresh (owner pid differs), so no lasting double copy, but for the dashboard the survivor may be the one that failed. Fix: after the replace, read the moved file's mtime/pid and, if it is not stale, put it back (or use a link/rename-to-unique-name check).
2. `common.py:181-185,129`, Windows. `open()` and `os.open` in Python do not share delete access, so `os.replace`/`os.remove` on a lock another process has open for that instant (a `lock_owner` read, the creator's write) raises PermissionError (an OSError). `take_lock` then returns False ("another starter owns it": a rare spurious refusal of a start), and `release_lock` swallows it and leaves the lock until it is stale (a restart in that window is refused for up to `stale` seconds). Rare, self-healing; no code change needed beyond knowing it. Watchdog reads only `stat`, so it does not trigger this.
3. Exit-3 handling by launchers is incomplete:
   - `tools/unwall.py` (loop refusal, `main()` returns None) and `keeper.sh` (`exit 0`) refuse with exit 0, not 3 as the brief and the other scripts do. The watchdog is unaffected (it only checks locks), but the convention is split.
   - `tools/dashboard/keep.cmd` is unchanged: on exit 3 (bind failed or lock held) it sleeps 3 s and retries forever, printing every 3 s. It only stops via its netstat check for `127.0.0.1:8099 LISTENING`, which misses a listener on 0.0.0.0 or ::. Harmless for a crash (the stale-lock wait is the intended retry) but should treat 3 as "already running, exit".
   - `.claude/skills/legion-session/SKILL.md` steps 2-6 say "restart it after an exit"; they do not mention that exit 3 means a copy already runs and exit 2 is the sentinel's wake. A main session that blindly relaunches on exit 3 just gets another 3 (harmless). `stackctl.py` launches none of these scripts. `watchdog-keep.cmd` handles 3 correctly (first start exits 0, later 3s retry until stale takeover; others filed as outage).
4. `keeper-lock.sh:20-22`, `keeper_take_lock` is `rm` then noclobber create, so two simultaneous keepers can both pass; the loser exits at its next `beat`. No trap releases the lock on exit, so a clean restart within 150 s exits silently with 0. Shell keeper only, rare.

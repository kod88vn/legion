## Major
- legion/chatjobs.go:216-224 (`chatAskKey`), bug b1794750152316-420: the dedupe key is channel|to|item only. It has no
  party, guild or speaker. Two different guilds (channel "guild") or two different parties (channel "party") asking for
  the same item (for example Shoes 2301) share one key, so the second group's ask is dropped for as long as the first
  waits (45-90 s, longer when listed). The caller `exchangeAsk` (exchange.go:586) has already recorded
  `exch.asks`/`askedAt` and returned true, so that bot never repeats the ask at that stage. The want then jumps to the
  next stage with no line said at all. That is a lost real request, not a duplicate. Fix: add the speaker's
  guild/party id, or the sorted hearers, to the key (the hearers list is the party/guild roster). The tests only use
  one hearer list, so they do not catch this. Harms live play (G-less, PR03: real players ask in their own guild), so
  it counts as major.
- legion/chatjobs.go:182-187: a dropped ask returns "" , the same value that means "template was said at once". Callers
  cannot tell, and the dropped speaker says nothing. Acceptable only once the key is per group (above).

## Minor
- tools/legionctl.py:157-158 (`local_hms`): the time is combined with the fixed date 2000-01-01 before `.astimezone()`,
  so a machine in a DST zone gets the January offset, one hour off in summer. Use the real date from the timestamp.
  Not an issue in November in most zones; the test does not catch it because it uses the same method.
- legion/api.go:85-106 (`charIndex`): the hypothesis is right and safe. It affects only the `byName` users in
  serveAPI (api.go:186 bots, :535-602 party create, :713 memory). All of them now resolve a shared name to the main
  character's bot instead of arbitrary last-wins, which is the intended behaviour. It does not touch name lookups
  elsewhere: `botByCharName` (guilds.go:396, used by chat-job answer validation and replies) still uses `botNames`, which
  is last-wins and case-sensitive, so `bot kaiz72` and a chat line to kaiz72 can still resolve to different bots. Not a
  regression; consider making `registerGuilds` use `charIndex` too. Mail was not found to use `byName`.
- legion/tuning.go:302: the new flag defaults on. reviewer.md says new behaviour defaults off, but PR37 (everything
  built is on) and the brief's request cover it; noted only. The dedupe is the only behaviour change; the CLI changes are
  tooling.
- tools/legionctl.py:508-521 (`bot`): `try_call` hides every failure (network down as well as 404) before the Ayla
  fallback; harmless, other names get a second `call` that reports the real error. The Ayla branch only reads
  `/api/meter/neo`, so it does not touch her (G05, G13 clean).

## Answered questions
- Dedupe after an answer: `chatAnswer` (chatjobs.go:411) and `chatJobsDue` (:275-286) remove the job from `open`, and
  `chatAskOpenLocked` only scans `open`, so a second request after the answer or after the deadline is queued
  (`TestChatAskDedupeAfterAnswer`). Only a still-unanswered ask for the same key is suppressed. Within one speaker,
  `exchangeAsk` already limits to one ask per 5 min, so the dedupe adds nothing there; its only effect is across
  speakers, which is why the key must be per group.
- `--channel #trade`: the missing value now gives a usage error instead of IndexError; `norm_channel` maps trade/global
  to #trade/#global. Paging and deadline conversion behave as tested.

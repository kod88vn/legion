# Review: fix/farmer-roster-tool 291e91a (WP4 farmerpick + addchars)

Reviewer: Sonnet. Scratch merge of main 754af66 + this branch: `python -m unittest discover -s tests/system` ran 353 tests, OK (1 skipped). Rules checked: G06, G11, G22, G23, EC45, design market-engine.md 2.1.

## Blockers

1. tools/system/addchars.py:95-96 (char_reg_num) writes `legion_first = 3` for the vendor. 3 is the Archer family (rathena/npc-custom/legion.txt:44,52). A Novice at job level 10 changes to the family in `legion_first`, so every added "blacksmith" vendor would become an Archer and then a Hunter or Bard. `tools/pairchars.py:29` (`VENDOR_PLAN = ('blacksmith', 5, 0, 10)`) writes 5 (Merchant family), and `legion/persona.go:563` writes `pl.First` (5 for blacksmith). The docstring claims "the same rows as tools/pairchars.py"; this row is not. The tests only count 3 statements and never check the value, so they do not prove the claim. Fix: 5 (taken from the plan, not a literal) and a test asserting `(cid,'legion_first',0,5)`.

2. tools/system/addchars.py:35,49 `ADD_MIN = 2104001`. personas.json has accounts 2100001-2104000 only (4000 personas, verified). The design (2.1) says 2104001-2199999 is for brand-new accounts "if ever needed"; the 65 phase-1 additions go to EXISTING guild-less accounts, all of which are <= 2104000. `check_add_account` therefore refuses every real account, so `--apply` can never insert anything for the intended roster. The tests pass only because fixture accounts sit at 2104001 and they assert 2100002 is "out of range". The safe bound is the bot range 2100001-2199999 (G06) plus the existing guards (login row in dump, no guild, no merchant char). The owner should confirm because the design text differs; I recommend widening.

## Major

3. addchars never updates personas.json (pairchars does, `tools/pairchars.py:136`, with a backup). The engine picks characters from personas.json, so an inserted vendor row exists in the DB but is never played; a re-run with a stale dump could plan a second vendor. Add a follow-up work package (append to personas.json with backup) or document the gap in the tool and HANDOVER.

4. Duplication: addchars.py is a third copy of the char/inventory/char_reg_num rows (pairchars.py, persona.go seedSQL) and it already drifted (blocker 1). Canonical writer today is `tools/pairchars.py` (also does personas.json, backup, human-party pinning, online check), but it works on ALL accounts with an unpaired hunter or vendor, not a chosen list. Recommendation: keep addchars as the list-driven farmer tool but share one row builder with pairchars so they cannot drift. pairchars already gave every hunter-plan account a vendor, which is why all 85 have one. Starter inventory (1201/2301/569/11500/501/601/602) and the other char columns match pairchars exactly; only `legion_first` differs.

## Minor

5. addchars.py:88-91 `sex` is interpolated unescaped (name is escaped by `_esc`). guard_sql catches a quote-breaking value (probed: raises), so not exploitable; still escape it or restrict to M/F/S.
6. guard_sql has no table allowlist: any `INSERT INTO <table>` passes, including `INSERT ... SELECT`. Statements are template-generated, so theoretical; an allowlist {char, inventory, char_reg_num} would make it a guarantee.
7. The human-party pin (human-parties.json) is only applied in farmerpick via the optional `--pinned`; addchars does not check it. The bot-range test already excludes humans (G06), so low risk; default `--pinned` to data/human-parties.json like pairchars.
8. `--live` uses the hard-coded `ragnarok` login via `wsl docker exec` (same as pairchars). Not reachable from tests (they replace `run_live`).

## Verified OK

- guard_sql adversarial probe. Blocked: DELETE/UPDATE/DROP/TRUNCATE/REPLACE/CALL/SET after `;`, lower and mixed case, `/*! */` and `--` comments, newline between words, backtick-quoted keywords, `ON DUPLICATE KEY UPDATE`, a second INSERT, backslash-quote tricks. Names with `'`, `;`, newline are escaped and stripped before the scan. Only `INSERT INTO ... SELECT` passes among non-template forms, and it is additive. Unicode lookalikes are not keywords to MariaDB. There is no DELETE/UPDATE code path in the tool.
- Refusals per account (tested): no login row, in a guild, existing merchant char, slot / char_id / name taken (case-insensitive), account out of range, invalid farmers.json.
- Dry run is the default. `--apply` needs `--copy DIR` or `--live`; `--copy` inside live legion/data is refused (G23); `--copy` plus `--live` is refused. Tests run under LEGION_TEST=1 and replace `run_live`; no test can reach ro-db.
- Dump format: header `account_id char_id char_num name class guild_id`; `char.char_num/class`, `guild_member.char_id/guild_id` are real rathena columns; `IFNULL(g.guild_id,0)` and `mariadb -B` TSV match the loader. The dump query exists only in a docstring; no script runs it, so ops need the exact command.
- `.gitignore` and `farmers.example.json` are fine. The engine reads farmers.json read-only (`legion/marketengine.go:636`); the extra keys (`detail`, `vendor_adds`) are ignored there.
- No behaviour is on by default; nothing deploys or runs live.

- Guild-less: 817. Of these, main (role main, slot 0) on a hunter-line plan: 85 (hunter 38, hunter_agi 19, hunter_blitz 18, hunter_trap 10), and all 85 already have a vendor. The fixer is right; the design numbers (432 / hunter 385) are wrong as stated.

- Phase 1 can honestly be 85 now with `vendor_adds` empty. Options to reach 150:
  a. Relax `main_char()` to "any hunter-plan character on a guild-less account that has a vendor" (347 more accounts): no DB write, no guild change, no human touched. The account's original main is then benched by the planned farmer rule in `pickChar` (design 2.1 already benches extras). Needs the owner's nod since the original main stops playing (Constitution 2.3: one person, one goal). Recommended; it avoids blockers 1-2 and major 3.
  b. Insert new hunters on guild-less non-hunter accounts (pairchars style, `legion_first` 3): more DB writes, not recommended.
  c. Run phase 1 at 85 and grow later.
  No option needs anybody to leave a guild (G20/G25 untouched).

verdict: do not merge

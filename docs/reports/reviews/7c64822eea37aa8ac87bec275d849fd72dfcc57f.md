- Major 1, CSRF / DNS rebinding: fixed. `write_refusal()` (dashserve.py ~:714) applies to every POST and DELETE: Host must be `127.0.0.1:<port>` or `localhost:<port>`, Origin must be exactly the dashboard origin (else Referer must be it or under it), Content-Type must be `application/json`, and the path may not contain `..`, `//`, `%` or a backslash. Live probe results: foreign Origin 403, `Origin: null` 403, no Origin and no Referer 403, rebound Host (with its own origin or the dashboard's) 403, `text/plain` 403, no Content-Type 403, `Origin` or `Referer` with a `.evil.com` suffix 403, same-origin 503 (reached the dead engine, as it should). Foreign-origin DELETE and the guarded status POST are also 403. A refused write drains its body and closes the connection.

## Pending-requests flow versus `tools/puppet/orders.py` (ba4d6fc)
- Reader. The dashboard's `pending_requests()` reads the same file (`C.dpath("ayla_override_requests.jsonl")` equals `orders.requests_path()`) and accepts `kind` in `request` or `order` with `id`, epoch `t` and `text`. Real rows from `orders.add()` (`{"kind":"request","id","t","iso","from","text","status":"pending"}`) are listed; I confirmed this by running it. Accepting `order` in this file is harmless.
- Status rows. `{"kind":"status","id","status":"confirmed"|"declined","by":"owner","t"}` is exactly what `orders.pending_requests()` treats as closing (it keys on `kind == "status"` and the id). Run live: after `append_request_status` on a real request, both readers report it closed. The append goes under a lock and only for an id that is currently pending, so unknown or answered ids answer 404.
- Confirm flow. Confirm opens the prefilled form (kind picker, value defaulting to the text, hours rounded up to an offered step). The override is POSTed first, and the order is marked confirmed only after the engine stored it (a 409 gate warning keeps the order open and "Force anyway" carries the callback). Decline posts the status only. The DOM tests cover this. The owner picks the kind, so nothing is parsed or steered from free text (AY25, G13 hold).

## Findings

### minor 1: the 24 h expiry is one-sided (`dashserve.py:704-720` against `orders.py:100`)
The dashboard drops an order older than 24 h from its list but writes no status row, and `orders.pending_requests()` has no expiry. I ran it: a 30 h old request is gone from the dashboard and still returned by `orders.pending_requests()`, so the watcher briefing (`briefing.py:494`, oldest first, `reqs[:10]`) keeps listing it as "waiting for the owner" for ever, and ten stale ones would hide newer ones. The owner cannot close it, because the dashboard no longer shows it. No effect on live play, only on the watcher's briefing. Fix either side: have the dashboard write a `declined` (`by: "expiry"`) row when it first sees an expired one, or apply the same 24 h cut in `orders.pending_requests()`.

### minor 2: `ctlSpots` still puts `s.MinLv`, `s.MaxLv`, `s.Mobs` into innerHTML unescaped (`dashboard.html` ~:1778)
Engine numbers, no practical risk (carried from the first review); wrap in `esc()`.

### minor 3: negative Content-Length blocks one handler thread (`dashserve.py:755`, `request_status`)
`rfile.read(-1)` waits for the client to close. Only reachable after the Origin/Host/Content-Type guard passes, so not from another site; clamp `n < 0` to 0 or answer 400.

### minor 4: DELETE and GET bodies
`do_DELETE` on the override route proxies without reading a request body. Harmless with the guard; noted only.

### note: the Host guard also refuses the dashboard reached by any name other than `localhost` or `127.0.0.1` (LAN IP, `[::1]`, a hostname). Writes then answer 403 with a clear message while reading still works. That is the intended trade for rebinding safety, but the owner should know.

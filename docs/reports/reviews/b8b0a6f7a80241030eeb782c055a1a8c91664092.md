## Major
- tools/dashboard/keep.cmd:11 (DB06): `if errorlevel 3 ... exit /b 0` stops the keep loop on any exit 3, but dashserve exits 3 for
  a transient cause too. After a hard kill (taskkill /F, power loss) atexit does not run, so `dashboard-8099.lock` stays fresh for up
  to 120 s (dashserve.py:789). keep.cmd restarts after 3 s, take_lock fails, dashserve returns 3, and the loop quits for good:
  the dashboard stays down until someone restarts keep.cmd. Before this commit the loop retried every 3 s until the lock aged out.
  The same happens when the bind fails briefly (dashserve.py:782). Fix: on 3 retry for about 2-3 minutes before giving up,
  or stop only when netstat shows the port really listening. (Windows abort() also exits 3, a minor extra.)

## Minor
- tools/rogui/keeper-lock.sh:44 `trap 'exit 143' TERM`: bash runs a trap only after the foreground command ends. keeper.sh uses
  foreground `sleep 20/60` and docker calls, so TERM is acted on up to 60 s late (measured in WSL: TERM at 1 s, exit after the 5 s
  sleep). The lock is still released. Harmless, but a keeper can no longer be stopped promptly by TERM; use `sleep N & wait $!`.
- tools/rogui/keeper-lock.sh:36-37 put-back uses `mv -n`, which is check-then-rename, not atomic. The window is tiny and the
  worst case is the aside copy being dropped while a fresh lock exists (the loser then exits on its next refresh). Acceptable.

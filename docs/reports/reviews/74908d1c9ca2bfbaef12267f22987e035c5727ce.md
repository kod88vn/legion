## Findings

### major 1: any web page the owner opens can write overrides for Ayla (CSRF and DNS rebinding) (AY25, G13 intent)
`dashserve.py:746-757` (`do_POST`, `do_DELETE`) and `:426-436`: the server attaches the owner token to any POST that reaches `/api/ayla/overrides`, with no Origin, Host, Sec-Fetch-Site or Content-Type check. A hostile page in the owner's browser can send a "simple" cross-site `fetch('http://127.0.0.1:8099/api/ayla/overrides', {method:'POST', mode:'no-cors', body:'{"kind":"farm_map",...,"confirm":true}'})` with `text/plain`. No preflight is needed, the proxy forwards the body, and the engine decodes the JSON whatever the Content-Type is. `confirm:true` also skips the 409 gate. A DNS-rebinding page can do the same, because Host is never checked. The token therefore protects nothing against the browser, which is the one thing it was added for. Fix: on POST and DELETE to the override route require `Origin` (or `Referer`) to be the dashboard's own origin, require `Content-Type: application/json`, and reject a Host header that is not the bound address or localhost. Add tests for the foreign Origin, the missing Origin and `text/plain` cases.

### major 2: path tricks still get the token (claim in the brief does not hold) (`dashserve.py:418`)
`OVERRIDE_ROUTE = ^/api/ayla/overrides(/[^?]*)?(\?.*)?$` accepts anything after the slash. I ran it: `/api/ayla/overrides/../x`, `/api/ayla/overrides/../../stats`, `/api/ayla/overrides//x` and `/api/ayla/overrides/%2e%2e/x` all match, and `Engine.call` forwards the raw path unchanged (urllib does not normalise it) with `X-Owner-Token`. So the browser can make the dashboard attach the token to a request whose cleaned path is another engine route. I did not run the Go engine; by reading the code, Go's ServeMux cleans the path and answers 301. For DELETE urllib raises and the 301 comes back as an error, which is harmless. For POST urllib follows 301 as a GET, keeping the `X-Owner-Token` header, so the token lands on a GET of an arbitrary `/api/...` route. Today the engine checks the token only on override writes, so nothing exploitable follows, but the guarantee relies on engine behaviour and is not enforced here. The tests cover `overridesX` and `?x=1` only, not `..`, `//` or `%`. Fix: tighten the pattern to `^/api/ayla/overrides(/[A-Za-z0-9_-]+)?(\?[^#]*)?$`, or reject any path containing `..`, `//`, `%` or a backslash before adding the header. Add those cases to `test_owner_token_only_on_override_writes`. These lines predate this commit (they are in main), but this commit is what opens DELETE to them.

### minor 3: `do_DELETE` forwards any `/api/` path (`dashserve.py:753`)
DELETE to any `/api/...` route is proxied, without the token. It cannot do owner writes, and the engine answers 405 on routes that do not take DELETE, but it is wider than needed. Limit it to `OVERRIDE_ROUTE`. `proxy("DELETE")` also never reads a body; a request body on a DELETE is left unread on the keep-alive connection.

### minor 4: unescaped numbers in innerHTML (`dashboard.html` ctlSpots, about :1763)
`s.MinLv`, `s.MaxLv` and `s.Mobs` from `/api/spots` go into `innerHTML` unescaped. They are engine numbers, so there is no practical risk; wrap them in `fmt()` or `esc()`.

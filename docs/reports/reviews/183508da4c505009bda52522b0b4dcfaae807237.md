## 4. addchars

- Rows: `plan_rows` calls the same `seed_rows`; test compares them to the pairchars path with the same rng. addchars
  seeds its rng with the account id, so a rerun gives the same rows; pairchars uses a shared rng, so the random hair/
  stat values differ between tools but the structure is equal. Fine.
- personas.json: the entry is appended in memory, then written atomically (`.tmp` + `os.replace`), with a timestamped
  backup made first. Entry fields equal pairchars' (`role vendor`, class 0, plan, target_class from the plan).
- `--copy DIR`: writes only DIR/addchars-*.sql and DIR/personas.json; live files are only read. The guard refuses
  the live data folder, and `--copy` + `--live` is refused.
- `--live` order: run_live (SQL) first, then backup, then atomic personas write (same order as pairchars).
  If the SQL fails: SystemExit before any file is touched, personas unchanged (good). If the SQL succeeds and the
  personas write (or backup) fails: the DB has the new characters, personas.json does not. Recoverable but manually: a
  re-run with a fresh dump refuses the account (slot / char_id / name taken), so the operator must append the entry by
  hand (the printed statements / the char ids are known) or delete the rows. The engine never plays the unlisted
  character, so no harm to play. pairchars has the same window. The SQL is also not wrapped in a transaction: a failure
  between the three INSERTs leaves a partial character (mariadb stops at the first error). Same as pairchars. See minor 2.

## 5. guard_sql probe (adversarial, run in isolation)

Refused: other tables (`login`, `ragnarok.login`, `ragnarok.\`char\``, `char_x`, `/*x*/ login`), `INSERT ... SELECT`
(also lowercase and `VALUES ((SELECT ...))`), `SET` form, second statement after `;` (DELETE or INSERT), `;` hidden in
`/* */`, `/*!50000 */`, `--` comments, backslash-quote string tricks, full-width semicolon / full-width `DELETE`,
`ON DUPLICATE KEY UPDATE`, `INSERT IGNORE`, `INSERT DELAYED`, tab or newline in the head, keywords in any case.
Accepted: only the three allowed tables in `INSERT INTO <t> (` form, and keywords inside quoted strings (names). No
bypass found. Only generator-built statements reach `run_live`.

### Minor
1. tools/system/addchars.py `copy_dir_safe` (live-folder check): compares `abspath` with a case-sensitive
   `startswith`. On Windows `--copy G:\RO\LEGION\DATA` (different case) is not refused, and `--apply --copy` would
   then overwrite the live personas.json without a backup (G23 breach by operator error). Use `os.path.normcase` and
   `os.path.realpath` on both sides. Not on by default; ops only.
2. addchars `--live` has no rollback or retry help for the SQL-ok / personas-failed case (section 4) and no
   transaction. Suggest printing the exact personas entries when the personas write fails, and prefixing the batch with
   `START TRANSACTION;` ... `COMMIT;` (mariadb rolls back an unfinished transaction on error exit). No test covers
   "SQL fails: personas untouched".
3. The dump query is still only in a docstring (from the first review); ops need the exact command.
4. addchars `build` default for the persona entry is `str-dex` for every vendor; pairchars copies the main's build.
   Cosmetic.
5. Rows differ from the old pairchars output only in the two cases listed in section 3 (backslash names, non M/F sex);
   both are improvements and cannot occur in the current data.
